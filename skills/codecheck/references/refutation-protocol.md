# 独立证伪协议：对每个正式候选重新核验

> Refuter 不是第二个 Scanner。它负责质疑发现的真实性、变更归因、影响和证据；新线索可以退回 Discover/Challenge，但不能在没有验证的情况下直接加入正式报告。

## 输入与独立性

输入一个或一组 `candidate_id`，完整可检查的**代码快照/基线与 Diff**、原始发现的严格命题（claim）、触发条件、已有证据、被引用的规格与执行记录。不应只给 Refuter 一段发现者写的总结，让它机械复述。

优先使用独立子 Agent/独立上下文来验证（平台支持且授权时）。若只能由同一模型审查，在新轮次采取**反向证明任务**：把候选视作可能错误，主动寻找最有力的防护、不可达性、平台保证、旧代码行为或误读；在 trace 中写 `independent_verifier: false`。

**全部正式候选必须复核**，不对 P2/P3 机械抽样。可以依据风险高低调整验证深度，但不能未经验证直接进入最终正式 Finding。

## 六项证伪问题

1. **Claim 是否准确**：指出实际代码、状态/数据转换、最小位置；检查每个额外的事实陈述，不仅验证结论。
2. **Trigger 是否可行**：从真实入口到故障点，检验前置条件、构建开关、线程顺序、调用者输入范围、权限与分发路径。
3. **Protection 是否已存在**：追踪上游/下游 Guard、类型与语言保证、锁、幂等性、回滚、资源生命周期；防护的作用范围和 build mode 是否覆盖触发场景。
4. **Impact 是否准确**：故障结果是什么、影响多大、需要什么概率/条件；避免把局部异常升级为系统级问题。
5. **Change attribution 是否成立**：对比基线/历史代码，属于本次新引入、显著加重、还是原本就存在？存量审计不要求新增归因，但必须标记。
6. **Evidence 是否充分**：直接证据、经授权测试、静态推导是否可复核？“两个模型同意”不是证据。

不要因为测试无法复现就自动 `refuted`；也不要因为代码存在某种风险关键词就自动 `confirmed`。防护只有在**确实覆盖该触发链且保证有效**时才能证伪，例如 release 构建中的断言不能被当成强制运行时 Guard。

## 裁决定义

| verdict | 使用条件 | 最终去向 |
|---|---|---|
| `confirmed` | 代码/规范证据构成可复核触发链、影响和变更归因；可以由严密的源码论证或实际测试支持 | 正式 Finding，依据真实影响定 P0–P3 |
| `refuted` | 已找到可靠反证，关键前提不成立或已有防护覆盖触发路径 | 只留 refute log，报告不计数 |
| `unresolved` | 存在实质疑点但关键可达性/契约/后果缺证 | 作为未决风险，不计正式 Finding、不赋确定严重等级；关键缺口可触发 `insufficient` |
| `out_of_scope` | 未在本次变更引入/加重，或超出授权范围；存量审计例外 | 只记日志，可作为非阻塞范围说明 |
| `merged` | 同一真实根因的多条候选被合为一条 | 被合并的候选不再独立计数 |

可在 verdict 旁记录 `severity_before/after`，但**升级/降级必须用后果证据论证**；`low likelihood` 不是普适的降级理由，必须结合触发条件和影响。

特别是高影响问题：要推翻可达性，必须明确给出足以排除特定触发条件的证据（如强制 Guard、生效的类型或构建时保证）；“很难复现”和“通常不会调用”都不够。

## 去重与根因合并

不要仅因两条发现同一行或同一文件就合并，也不能简单按建议“加个判空”合并。判断它们是否拥有**相同的失败机制与独立可执行的修复单元**：

- 相同前提破坏/相同实际根因，不同症状可以合并，并保留主要影响和所有相关位置；
- 不同根因即使同 `file:line`、同一 API 或建议相似，仍应保留独立项；
- 一个 Concern 引出的公共调用者回归和另一个 Concern 的独立修复，不应为了减少发现数而被误合并。

## 新线索反馈机制

Refuter 发现新的高价值风险时记录：

```yaml
feedback:
  concern_id: C02
  new_question: "<新的可证伪问题>"
  evidence: ["<真实 file:line>"]
  recommendation: "return_to_discover|return_to_challenge"
```

交回检视负责人，形成新的 candidate 后**重新走完整 Refute**。一个新疑点不因出自 Refuter 就能绕过验证。

## 输出记录

`refute_log_<scope>_<date>.md` 必含：审查环境与范围、每一候选 ID、初始主张、检查过的路径/防护/证据、归因、裁决、原始及最终严重等级（若有）、合并目标、下一步动作和未决风险；检查不了的步骤也要明示。

从未执行测试不得写“复现失败”；引用规范应带来源版本/位置；所有结论与 `review_trace` 内的候选结果一致。
