# Codecheck V2：自适应、证据驱动的代码检视

## 目标

在用户授权范围内发现**真实、可行动、可复核**的代码问题，并明确尚未解决的高价值疑点与检视边界。优先保证有效问题发现率、证据质量和人工复核价值，而不是报告条数或检查项数量。

**探索方向由代码决定；事实判断由证据决定；交付质量由统一契约保证。**

## 硬约束（必须满足）

1. **范围真实**：明确检视目标、比较基线、相关排除项和环境限制。不能将存量问题冒充本次引入的问题，也不能无说明地扩大审查范围。
2. **理解先于结论**：先阅读变更及必要上下文，按独立行为/契约变化建立 Concern Map。基础检视应覆盖识别出的 Concern 及有实质关联的交互；不能仅凭修改行或关键词下结论。
3. **证据真实**：正式 Finding 必须有实际源码位置、可解释的触发条件、受影响的行为或不变量、具体后果和可追溯证据。不能把猜测、未经执行的测试或模型间相互同意写成已验证事实。
4. **知识按需、来源可查**：需要外部规则裁决时，从 `abilitykit_sdd` 的 `standards/`、`specifications/` 等适用资料中查找原文，核对版本和前置条件。没找到或无法访问时记录未知；不编造条款，不把历史案例当作自动成立的规范。
5. **结论必须经证伪检查**：每个拟进入正式报告的候选，都要检验可达性、现有防护、真实影响、基线归因及重复根因。证据不足的候选列为未决风险；无法复现不等于已证伪。
6. **遵守权限边界**：默认只读，不修改待检视源码，不运行未经授权的仓库程序、不自行安装依赖或联网下载资料。必要的动态验证须在获准的隔离环境中进行；如实记录 `not_run`、失败和限制。
7. **交付契约固定**：机器报告使用固定 17 字段与评分权重（`schema_version: 2.0`）；`dimensions_*` 取值域为 V2 能力名 `behavior/security/input/api`，记录实际检视覆盖，不声明任何 Scanner 运行记录；以 V2 trace 如实记录 Concern、实际调查、知识引用、攻防和证伪。

## 工作方式：先基础检视，再按风险深入

| 工作环节 | 要作出的判断 | 执行要求 |
|---|---|---|
| **界定范围** | 检视什么、相对哪个版本、允许使用哪些工具？ | 必须明确；无法确定时记录假设和限制 |
| **理解与发现（Understand / Discover）** | 改变了哪些行为？哪些前提或保证可能被破坏？ | 对识别出的 Concern 做基础检视；动态选择调查路径 |
| **主动挑战（Challenge）** | 哪些“看似正确”的假设最值得尝试推翻？ | 基础检视后根据风险与信息增益选择；高影响路径不能无理由跳过 |
| **独立证伪（Refute）** | 发现真的能触发吗？现有防护是否已覆盖？ | 所有拟作为正式 Finding 的候选必须复核 |
| **整合交付** | 哪些问题确认、哪些未知、哪些未覆盖？ | 必须检查覆盖、去重、报告与 trace 一致性 |

这些环节是**质量责任和必要的信息依赖**，不是固定的多 Agent 流水线。可以在发现关键新证据时回到前面补查；不要求每次采用相同的工具、探索顺序或攻防轮数。

### 如何确定检视范围

优先遵循用户明确给出的 PR、commit、diff、文件或路径。仅说“检视本次修改”时，优先查看工作区及暂存区；若均无改动且上下文明确指向最新提交，可检查 `HEAD^..HEAD`，并记录选择依据。仅给定路径而无版本差异时按**存量审计**处理。不要猜测不存在的目标基线。遵循仓库 `AGENTS.md` 的范围约定，用户明确要求覆盖的路径除外。

### 如何决定检视角度和深度

- 从实际执行路径、调用者与消费者、状态变化、资源所有权、边界约束及跨 Concern 交互中**自主提出可证伪问题**；示例和技术分类都不能变成固定 Checklist。
- 基础检视完成后，选择**潜在影响大、当前假设不确定、且有可能通过进一步查证得到新证据**的对象进行 Challenge。构造实际允许发生的反例，沿源码检查可达性与防护。**不规定反例数量**，也不因“列出一个反例”就认为攻防已完成。
- 对纯格式或已证实不改变行为的低风险 Concern，可以标记 Challenge `not_applicable` 并给出理由。对重要风险若因上下文、时间或验证环境不足未能深入，应记为 `limited`，而不是假装完成。
- 调用链深度、外部规格查询、静态工具、独立子 Agent 和隔离测试均按实际收益选择。多项相对独立的 Concern 才考虑并行；最终仍需检查它们之间的交互。
- 继续探索的依据是**尚存在值得验证的新假设或证据缺口**。当进一步调查难以带来有意义的新结论，或达到授权/预算限制时停止，并明确保留未决风险；不要为了完成预设轮数重复思考。

## 交付与完成判定

应产出以下三个文件，互相引用并保持内容一致：

- `codecheck_report_<scope>_<date>.md`：按 [`codecheck_report_TEMPLATE.md`](codecheck_report_TEMPLATE.md) 生成的报告及机器门禁元数据。
- `review_trace_<scope>_<date>.json`：真实的 Concern 覆盖、调查证据、知识引用、挑战和限制。
- `refute_log_<scope>_<date>.md`：每个正式候选的验证、证伪、未决或合并记录。

交付前确认：**每个 Concern 的基础检视状态可核对；重要挑战有实际假设与检查记录或明确限制；每个正式 Finding 均已证伪核验；未决问题没有混入确定等级；报告与 trace 的计数、评分、覆盖一致。**

在有 Python 环境时运行：

```bash
python3 skills/codecheck/scripts/validate_report.py <report.md> --trace <review_trace.json>
```

此校验只核对结构与可计算规则，不能代替缺陷事实的独立判断。无运行条件时说明原因，并人工核对相同约束。**没有发现问题不等于证明没有问题；关键行为无法判断时应诚实标记 `insufficient`。**
