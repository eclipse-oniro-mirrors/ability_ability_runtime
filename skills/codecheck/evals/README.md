# Codecheck V2 评测：衡量真实问题发现率

本目录先提供评测协议与校验单测；**尚未执行任何生产代码检视实验**。`test_gate_contract.py` 仅测试报告数据契约，不代表真实 Bug 发现准确率。

## 推荐的真实历史回放

收集在 ability_runtime 中**已知真实、人工确认、后续修复过**的提交：每个用例至少保留：

- `case_id` 与目标代码的 `base_sha`、有问题的 `target_sha`；
- 人工确认的根因、触发条件、影响、优先级，以及支持该问题的代码位置；
- 证明问题存在的最小条件或原始复现；
- 修复提交仅供**盲评裁决方**使用，不能给检视执行者提前查看；
- 是否是无问题负样本（可混入正常重构或已被保护的可疑代码）。

让所有版本在相同代码状态、同一模型、相近上下文预算和工具权限下审查，不得把后续修复的源代码、提交说明或金标准问题文本泄漏给模型。

## V2 指令优化对照（先验证这次修改）

本次优化删除了身份设定、取消反例数量配额，并缩短主入口指令。建议将**上一版 V2 与本版 V2**作为对照，其他条件不变：同一模型、检视范围、外部知识库版本、工具权限、报告契约和预算。分别比较真实缺陷的召回率/准确率、Challenge 增量有效发现、无意义反例比例、未决风险记录完整度和 Token 消耗。不要把“Prompt 更短”直接当作质量更好。

可混入简单无行为变更与复杂跨模块行为变更：简单修改验证是否允许合理跳过攻防，复杂修改验证是否仍能自主深入、及时停止且不掩盖未决风险。

## 消融矩阵

| 实验组 | 配置 | 回答的问题 |
|---|---|---|
| A | 旧 scanner + patterns + refute | 原有有效召回率/误报成本 |
| B | V2 Understand + Discover + KB | 动态 Concern-based 检视提升了什么？ |
| C | B + Challenge | 攻防是否带来**B 没有发现**的独立问题？ |
| D | C + 独立 Refuter | 误报是否下降？有多少真实问题被错误推翻？ |

在实验中保留所有原始 trace，不挑选最优重试充当单次成绩；多次试验记录分布与不稳定性。

## 最小评测指标

- **Recall** = 已发现且根因正确的真实缺陷数 / 本批真实缺陷数（以人工裁决为准）。
- **Precision** = 人工确认有效的独立正式 Finding 数 / 所有正式 Finding 数。未决问题单独统计。
- **Top-5 Precision**、每项真实缺陷平均需要多少人工复核时间，以及单次 token/工具调用开销。
- Challenge uplift = C 中新增、B 未发现且人工确认有效的缺陷数；还要统计新增误报。
- Refuter false dismissal = 被 Refuter 推翻却是金标准真实问题的数量。
- 质量审核：引用是否真实、候选触发链是否可达、规格版本是否适用、报告中有没有把 `not_run` 冒充执行过。

## 裁决注意事项

每个 Finding 必须能与 ground truth 的**同一根因**匹配；只重复提到受影响文件/关键词不算真正检出。两种不同措辞但同一根因不重复计 TP；与评测预设不同但确有证据的新有效问题单列 `valid_additional`，不能自动当误报。

至少两名具备业务经验的人工裁决者独立判定有争议的项目，保留证据与分歧结果；报告结果要区分合成用例与真实历史缺陷，不得将一个小样本的百分比分数宣称为生产环境准确率。

## 可立即运行的机器合约单测

```bash
python3 -m unittest discover -s skills/codecheck/evals -p 'test_*.py' -v
```

报告 YAML 合约测试需要 PyYAML；知识检索测试使用标准库。二者均不需要真实业务仓库或远程知识库。
